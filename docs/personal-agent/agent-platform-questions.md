# OpenDot：Agent 平台问题白话解答

这份说明把今天讨论的业务、Runtime、上下文、授权和群聊协作问题放在一起。尽量用日常语言解释；每个问题都配一个小例子。例子是为了说明机制，不代表真实用户案例或本次实测结果。

先记住一个简单分工：

- **模型负责理解和表达**：读懂用户要什么，组织答案，提出下一步建议。
- **OpenDot 后端负责规矩**：谁能访问什么、能不能调用工具、预算还剩多少、状态怎么保存。
- **Runtime 负责把工作跑起来**：管理模型会话、工具任务和恢复。
- **外部服务负责实际的外部动作**：模型供应商、MCP Server、消息平台、Mem0 等。

因此，“模型说做完了”不等于任务真的完成；需要看系统保存的状态和外部回执。

## 一、项目到底解决什么业务问题？

### 1. 谁是目标用户？他们的真实痛点是什么？

项目把个人和小团队当作目标用户：他们想有一个可以持续接收任务、保留工作上下文、使用获准工具，并能在不同设备或聊天平台查看进展的助手。

可以把产品假设说成：**用户现在要在聊天、文件、自动化、工具权限和任务进度之间来回切换；OpenDot 想把这些东西放到一个有边界的工作台里。**

但这是从产品设计推出来的假设，不是市场研究结论。仓库里没有明确的用户访谈记录、用户数量、客户案例或线上使用数据。不能说“已经有真实用户证明了这个痛点”。

**例子：**一个人可能在聊天里接任务、去文件夹找资料、再到另一个平台看审批进度。OpenDot 的设计想把这些步骤接起来；但这个例子只是可能的工作流，不代表已经访谈证实。

### 2. 哪些事必须用 AI？哪些不应该交给 AI？

AI 适合处理没有固定答案的事，例如理解自然语言、写内容、归纳资料、根据对话提出建议。

下面这些事则应该由普通程序按明确规则处理，而不是让模型决定：

- 用户身份、Workspace 权限和授权是否有效；
- 输入有没有重复、队列顺序是什么、预算是否用完；
- 工具参数是否符合审批内容；
- 文件路径是否合法，任务状态能否从当前状态转移；
- 外部消息有没有收到平台回执。

AI 加进来以后，也增加了新的麻烦：模型可能理解错、胡编、受恶意文本影响、超出上下文、遇到供应商故障；还可能发生“工具已经执行，但回复在路上丢了”的情况。授权和回执机制是为了管理这些风险，不代表风险从此不存在。

**例子：**模型可以读懂“找上周的决定并写个摘要”；但“这个用户能不能看该 Workspace”必须由后端检查，而不是让模型自己判断。

### 3. 怎样才算成功？源码能证明效果吗？

要把三种“成功”分开：

- **任务成功**：开始前就有能检查的目标；完成后结果符合目标，必要时由用户确认。
- **工具调用成功**：参数通过检查，工具返回有效结果，或有可核验的副作用回执。
- **外部投递成功**：外部平台给了接受或投递回执。这通常仍不代表对方已经阅读。

源码能告诉我们系统怎样判断状态，测试能告诉我们某些场景是否按预期运行；两者都不能替代真实用户的成功率、节省时间、满意度或付费意愿。

仓库记录过真实模型的本地测试，也保留了之后失败的记录。这是有价值的工程证据，但不足以证明线上稳定或用户真的获益。要回答“效果好不好”，还需要真实任务样本、旧工作流基线、失败率、人工介入率、重复副作用率、外部投递回执和用户反馈。

**例子：**模型生成了“报告已发出”不算投递成功；要看消息平台有没有返回接受回执。即使平台接受，也不能据此说收件人已经读过。

### 4. 系统和外部服务的边界在哪里？

大致可以这样理解：

| 部分 | 谁提供什么 |
| --- | --- |
| OpenDot 后端 | 用户、Workspace、权限、队列、审批、业务状态和连接外部服务的适配代码 |
| Pi Runtime | Agent 会话、原生任务、工具执行框架和相应的恢复能力 |
| 模型 Provider | 真正的模型推理、模型服务可用性、模型上下文限制和供应商账单 |
| Docker | 容器隔离和进程运行环境；OpenDot 负责选择挂载、环境和执行策略 |
| MCP Server | 实际提供某个工具功能；MCP 协议本身不保证外部操作只执行一次 |
| Mem0 | 可选的外部记忆服务；服务接受数据不代表记忆已经提取或可搜索 |
| Langfuse | 可选的观测接收端；接收请求不代表内容已经出现在项目页面上 |

OpenDot 的业务状态主要在 SQLite；Pi Durable 的会话和任务检查点在每个 Session 对应的原生存储里；云端 Runtime 使用自己的持久化方式。邮件、设备控制、MCP 写操作和聊天投递发生在数据库事务以外，所以不能假设“本地 SQLite 提交了，外面就一定成功”。

**例子：**OpenDot 可以保存“准备发送邮件”的审批和调用记录，但邮件服务实际有没有发出，要看邮件服务的回执；本地数据库不能替远端服务作证。

### 5. 能不能从仓库直接证明某个人做了哪些贡献？

不能。代码和测试可以说明项目里有什么实现；提交和 PR 可以提供作者、变更范围和评审记录；但单凭代码无法证明某个人亲自做了设计、调试、评审或现场演示。

整理个人贡献时，最好把每项工作对应到具体提交/PR、讨论记录、测试输出或演示，并分清楚哪些是自己完成的、哪些是 Pi 或其他依赖提供的、哪些由其他协作者完成。本次整理只是在读源码和文档，没有修改或运行项目验收。

**例子：**“我写了某个模块”最好能指向具体 PR 和代码差异；“我验证了恢复能力”还应能指向本人运行的测试记录，而不能只引用仓库里历史上有这个测试。

## 二、Pi Durable 和运行可靠性

### 1. Pi Durable 和 `PiDurableRuntimeAdapter` 分别做什么？

把 Pi Durable 想成“底层发动机”：它管理原生对话、任务、提交和检查点。

`PiDurableRuntimeAdapter` 是 OpenDot 装在发动机外面的“转接头”：先检查 OpenDot 的 Session、用户和 Workspace 是否对应，再把输入交给 Pi Durable，把结果和状态接回 OpenDot。它不应该让模型绕开产品的授权。

**例子：**用户发来一条消息时，Adapter 先确认这条消息属于哪个 OpenDot Session，再交给 Pi Durable；Pi 跑完后，Adapter 把结果交回产品层保存和展示。

### 2. 为什么有单独的 `.owner.sqlite`？

一个 Durable 数据库同一时间只能有一个执行进程。`.owner.sqlite` 是一把本机的“数据库占用锁”：适配器通过 SQLite 写事务占住它，别的适配器就不能同时启动同一份 Durable 数据。

它不保存对话，也不是靠计时到期的租约。进程正常退出或被系统杀掉，操作系统释放锁；只是进程卡住或暂停时，不会因为等了几分钟就让另一个进程抢走。

**例子：**如果两个服务进程同时想打开同一份 Session 数据，先拿到这把锁的进程继续运行，另一个应失败退出，而不是两边同时处理同一任务。

### 3. 输入去重为什么不能只看 request ID？

只看 ID 会有危险：第一次请求是“帮我整理”，第二次却用相同 ID 发送“帮我删除”，系统可能把第二个请求当成第一次的重试。

所以 OpenDot 还把请求内容（以及适用时的队列模式等字段）算出摘要并保存。相同 ID、相同内容可以恢复同一份收据；相同 ID、不同内容就报冲突，不接受伪装成重试的新请求。

**例子：**`request-7` 第一次内容是“总结文档”，重试仍是“总结文档”就接回原结果；若内容改成“删除文档”，即使 ID 一样也必须拒绝。

### 4. 为什么 `dispatching` 崩溃后不直接退回 `approved`？

`approved` 表示“用户同意了，还没开始发出去”；`dispatching` 表示“已经到了可能发出外部请求的边界”。

进程在这个阶段崩溃，外面可能已经做了事，也可能还没做。直接退回 `approved` 再发一次，可能让同一封邮件、付款或设备指令执行两次。所以跨过派发标记以后，不能当作肯定没执行。

**例子：**付款请求发出后服务进程崩溃；如果一恢复就再付一次，用户可能被扣两次。系统应先查支付方回执，查不清就保持不确定。

### 5. `uncertain` 到底表示什么？

它表示：**我们知道请求已经进入可能产生副作用的阶段，但不知道外部到底做没做，或者本地没能可靠保存结果。**

它不等于“肯定成功”，也不等于“肯定失败”。这种状态不能自动重发；需要外部查询、稳定幂等键或人工核对来解决。

**例子：**控制设备的命令已经发出，但设备掉线、确认消息没回来。我们知道“命令尝试过”，却不知道设备有没有执行，这就是 `uncertain`。

### 6. `.owner.sqlite` 能不能让多台机器一起选主？

不能。它是基于本地 SQLite 文件锁的协作机制，依赖同一台机器和本地文件系统的锁语义。把文件放在网络盘、让不同主机共同使用，或者换一种锁语义，都不能据此推断它仍然可靠。

多节点要用真正的分布式协调机制，并配合带代数/栅栏值的 owner 身份、持久状态和外部副作用回执。单纯换成另一个数据库并不会自动解决所有问题。

**例子：**两台主机都能访问共享盘时，不能假设 SQLite 文件锁一定能阻止两边同时运行；需要专门的分布式锁/租约和旧 owner 栅栏方案。

### 7. 老的 owner“租约过期”后回来怎么办？

这里先纠正一个容易混淆的说法：**本地 `.owner.sqlite` 没有 TTL 租约，因此不存在“到点过期后新进程自动接管”这件事。**

其他带 lease 的业务（例如某些任务领取流程）要依靠单调递增的 token/epoch 做栅栏：新 owner 接管后，旧 token 的结算必须被拒绝。MCP 外部调用还会检查数据库里的 `dispatch_owner` 和状态；恢复者把旧的 `dispatching` 变成 `uncertain` 后，迟到的旧 owner 不能再把它改写成新的 `completed`。每种 lease 都要看自己的实现，不能把它们跟 Durable 本机锁混为一谈。

**例子：**任务先由 A 领取，后来 B 用更新的 token 接管。A 即使恢复并提交结果，数据库也应发现 A 的 token 已过期，拒绝它覆盖 B 的状态。

### 8. 哪些测试覆盖了这些边界？今天实际运行过吗？

仓库里的相关测试包括：

- `tests/pi-durable-input-ledger.test.ts`：同一 ID 的相同内容重试、不同内容冲突、并发竞争和历史未验证输入；
- `tests/pi-durable-ownership.test.ts`：多进程争用、进程退出后的重新打开和路径别名；
- `tests/mcp-approval.test.ts`、`tests/mcp-approval-process-recovery.test.ts`：审批、丢失回执和进程在派发前后崩溃；
- `tests/durable-mcp-native.test.ts`：原生 Durable 工具任务来源验证和撤销场景。

这些测试文件和历史验收文档记载了项目曾进行的验证，但**本次整理没有运行这些测试**。不能把仓库的历史记录说成我今天刚跑过的结果；也不能把模拟模型和 fixture 服务说成真实供应商验收。

**例子：**Fixture MCP Server 可以模拟“写入一条记录后丢响应”，证明代码不会自动再发一次；但这不能证明某个真实支付服务也遵守同样的幂等规则。

### 9. 如果扩展到多节点，不能只换数据库，还要改什么？

至少还要重新设计：谁拥有 Session、如何选主和续约、旧 owner 如何被栅栏、任务和输入如何去重、状态怎样原子更新、外部副作用怎样获得幂等回执、故障后怎样接管，以及跨节点的备份和恢复。

数据库能保存状态，但它本身不知道外部邮件有没有发送、设备有没有动作。要把副作用协议一起设计进去。

**例子：**多节点版除了换数据库，还要让每个节点在执行付款前检查当前 owner token，并让付款接口按同一个操作 ID 去重；缺一边都可能出现旧节点继续操作。

## 三、Prompt、上下文和 Skills

### 1. PromptPlan 的内容从哪里来？怎么知道来源？

固定提示词来自 Runner 的 Prompt 文件、平台规则、当前渠道规则和 Agent Profile 的身份/行为内容。Runner 根据当前功能是否启用，再决定要不要加入相应 block。

每个 block 会带名字、版本、作用范围、所属来源、是否必需、启用条件和内容摘要；整个计划还有总摘要。这样能比较“这次运行用了什么版本的提示词”，但不会把所有完整提示词文本都塞进审计记录。

每轮还会加入动态内容，例如本轮 Workspace Memory、Owner Profile、私有召回和频道上下文；这些并不都属于固定 PromptPlan。

**例子：**系统规则像书的固定章节；本轮用户说的“请用表格回答”像临时便条。审计能记录这次用了哪些章节和来源，但动态便条还可能由每轮单独加入。

### 2. 必需块、重复块和大小限制在哪里检查？

PromptPlan 生成时检查必需块是不是空的、block ID 有没有重复，并计算最终拼接文本的大小。大约到 50,000 个估算 tokens 会警告，到 100,000 会拒绝运行，而不是偷偷截掉提示词。

另外还有 SDK 提供的模型上下文用量检查。它检查启动时固定资源的大致用量。二者检查的对象不同，不能把其中一个当成另一个。

**例子：**如果必需的“安全规则”是空的，计划本身就不合格；如果计划有 101,000 个估算 tokens，则会因硬阈值被挡下。通过这两项仍不代表长对话不会溢出。

### 3. 静态预算和实际上下文有什么区别？

静态预算是启动时能大致数出来的东西：系统提示词、工具说明、Skills、项目规则等。它通常不包括整个对话历史。

Runtime 的实际用量会随着历史对话、工具结果和附件变化；Provider 的 token 计算也可能与本地估算不同。所以静态预算通过了，只代表“启动材料看起来没超”，并不保证完整请求永远装得下。

**例子：**启动时提示词和 Skills 占 20,000 tokens，但后来对话累积了 150,000 tokens，再加上工具结果就可能超过模型窗口；只看启动预算看不出来。

### 4. Skill 怎么从“发现”走到“Runner 真正加载”？

系统先从内置、用户、项目、Workspace、宿主机和 Plugin 等位置发现候选 Skill，再应用优先级、启用状态和 Agent Profile 的精确选择策略，生成统一清单。每个 Skill 的完整目录内容有摘要。

Host 和 Container 根据同一份有效选择去准备运行目录：Host 同步被选中的目录，Container 只读挂载选中的 Skill。Pi Runner 再从对应目录加载它们。审计里保留选择 ID 和清单摘要，便于比对“计划选了什么”和“实际配置是什么”。

不过，清单生成后磁盘内容仍可能变化，最终是否被某个 Runtime 正确加载还要通过运行时审计和集成测试检查。

**例子：**Agent 只选择了 `review` Skill，Host 和 Container 都应只给 Runner 这一个 Skill；若运行目录里多出未选的 `deploy`，就说明实际挂载与清单不一致，需要阻止或调查。

### 5. 明确选择的 Skill 被删掉或禁用怎么办？

应该直接报配置错误并停止这次运行，不能悄悄忽略、找个同名 Skill 顶替，或假装原来的能力还在。当前实现会检查明确选择项是否有有效目录和 `SKILL.md`，不可用时作为 `agent_profile_unavailable` 处理，不做没有意义的重试。

**例子：**用户明确选择了 `review`，但它被删除了；正确行为是告诉用户这个 Skill 不可用，而不是自动换成另一个来源的同名 Skill。

### 6. 预算预检通过，模型仍说上下文太长怎么办？

先由 Runtime 使用自身的上下文压缩/历史管理机制处理。Pi Runtime 有原生 compaction；旧的 Runner 路径也有自己的溢出处理。但如果压缩后仍超出 Provider 的限制，就会返回明确错误，交给 Runner 和上层处理。

不同 Runtime 的处理路径并不完全一样。预算预检是提前发现明显问题，不是对模型调用成功的保证。

**例子：**Pi Runtime 可能先压缩旧对话；如果 Provider 仍返回“上下文太长”，系统应显示失败原因，而不是把这次任务记成成功。

### 7. 多租户怎样防止不同 Workspace 的内容串在一起？

不能靠 Prompt 写一句“不要泄漏”来实现。真正的边界要在后端：按已认证用户和 Workspace 找数据；模型不能自报一个别人的 Workspace ID；Skills、Memory 和文件路径按所有者/Workspace 定位；Runner 只挂载当前有权使用的资源。

例如 Workspace Memory 请求里不接受模型传入的 owner/workspace 身份，Host 会从当前 IPC 和已登记 Workspace 解析它。每轮重新取当前 Workspace 的记忆快照，不直接沿用旧工作区的数据。

**例子：**A 工作区的模型即使在文本里写着“去读取 B 的记忆”，后端仍按 A 当前绑定的 IPC/Workspace 查数据，不照抄模型写来的 B 身份。

### 8. 现有测试证明了什么，又没证明什么？

测试覆盖了 Prompt 顺序、来源摘要、重复/空块、大小阈值、Skill 优先级与缺失、Workspace Memory 请求边界等代码行为。

它们没有证明每个真实模型的 tokenizer 都与估算完全一致，没有证明模型总会遵守指令，也没有证明摘要完全无损或所有现实攻击都不能造成跨租户泄漏。这些需要真实 Provider 验收、对抗测试和数据审查。

**例子：**单测可以验证预算函数在 80,000 时返回 hard limit；它不能证明每家模型的真实 tokenizer 都会把同一段文本算成相同数量。

### 9. 如果以后加摘要，如何避免把关键信息弄丢或把权限弄宽？

每条摘要都应记录它来自哪些原文/记忆、版本、所属 Workspace、摘要器版本和生成时间，并且能回查原文。先按权限筛选，再做摘要；不同 Workspace 的内容不能混在一起生成一条共享摘要。

测试时要检查关键事实、否定句、时间、冲突和来源有没有保留；还要用带不同 Workspace 标记的测试数据确认不会串租户。摘要是“压缩后的参考材料”，不能变成比原文权限更高的新指令。

**例子：**原文是“不要在周五前发布”，摘要不能漏掉“不要”和期限；并且摘要要能指回原消息及其 Workspace，不能被另一个 Workspace 直接复用。

## 四、MCP Session Consent 和单次工具审批

### 1. Session Consent 绑定什么？配置改了怎么办？

Session Consent 像是“这个 Session 可以启动这个 MCP Server，并开放这些工具”的授权单。它会绑定用户、Session、Workspace、Dot、Server 配置摘要、选中的工具、Server 来源、有效期和取消代数；设备工具还会绑定设备授权。

启动和调用时，服务端会重新核对当前配置。Server、Profile、Workspace、权限或设备授权发生变化，旧授权就不再适用；要按当前配置重新确认。不能拿旧授权悄悄扩大工具范围。

**例子：**原来只允许 `calendar.read`，后来 Server 配置新增了 `calendar.delete`；旧 Consent 不能因此自动获得删除权限。

### 2. 为什么每次调用还要参数摘要？

Session Consent 只说明“这个工具可以被使用”，并没有同意模型以后用任意参数做任何事。

每次调用还要把工具身份、参数、权限和来源锁定在一个摘要里。用户审批的是这一个具体动作；如果参数后来变了，旧审批不能拿来继续用。加密保存的参数在真正执行前也会再次核对。

**例子：**审批内容是“给小王发 10 元”，执行前参数若被换成“给小李发 100 元”，摘要就不匹配，系统必须拦住。

### 3. 什么时候从 `approved` 进入 `dispatching`？谁能写 `completed`？

`approved` 是“用户同意了，但还没发出请求”。代码最后一次检查工具目录和权限后、真正调用 `tools/call` 前，会在数据库里把它改成 `dispatching`，同时记下哪个执行者获得了派发权。

只有这个执行者收到并验证结果后，才能用匹配的执行身份把状态记为 `completed`。模型不能自己把调用标成完成。

**例子：**模型提出“删除文件”只是提议；用户批准后，Host 在真正发出删除请求前写 `dispatching`，最后只有 Host 根据实际回执才能写 `completed`。

### 4. 相同 request ID、不同参数会怎样？

会作为冲突拒绝，不会覆盖旧请求。项目对输入、Consent、工具调用和审批决定分别绑定请求内容/摘要。同 ID、同内容才可以作为重试拿回旧回执；同 ID、不同内容就不能冒充同一件事。

**例子：**审批决定 ID `dec-1` 第一次表示“批准删除 A”，重试仍是同一决定可返回旧回执；若改成“拒绝删除 A”，就必须报冲突。

### 5. 为什么 `uncertain` 不能自动当成失败重试？

因为工具请求可能已经到达外部服务。超时或断线只说明本地没有拿到可靠回执，不说明外部没执行。自动重试可能重复扣费、发消息或控制设备。

要么用远端能查的幂等键核实，要么让人处理；证据不足时就保持 `uncertain`。

**例子：**消息服务超时了，不能直接把“发送失败”当真再发一遍；可能第一条已经送达，只是确认丢了。

### 6. 这套账本覆盖了哪些工具？

它覆盖接入 `createDurableMcpTools()` 的、经过 Session 授权的 MCP 调用。设备类 MCP 还要满足设备自己的授权协议。

它不是全项目所有工具的通用事务层。比如读 Workspace 文件有自己的路径/ACL 检查；创建私有文件有独立的审批与文件回执；没有接入 MCP adapter 的插件或其他服务，也不会自动获得 MCP 的审批账本。

**例子：**`read_workspace_file` 走 Workspace 文件授权；MCP 的 `send_email` 走 MCP Consent 和单次审批；它们可能共享用户身份，但不是同一段工具账本代码。

### 7. 工具执行中撤销权限，会发生什么？

如果请求还没发出去，撤销可以阻止它派发。如果已经派发，撤销无法让外部动作倒回去；本地会阻止之后的调用，并根据结果时序保存 `uncertain` 或已完成回执。

即使外部动作完成了，撤销后也可以不再把结果交给模型。关键是不能为了隐藏结果，就把账本伪装成“外部动作从没发生”。

**例子：**邮件发送到一半时用户撤销授权，系统可以阻止后续调用并不再把邮件正文交回模型，但不能声称邮件一定没发出去。

### 8. 怎样测试“请求已经发出，但响应丢了”？

测试服务在收到工具调用时先写一条独立的“副作用发生”记录，再丢掉响应或杀掉执行进程。重启后检查本地状态是不确定、原调用身份没变、请求没有自动再发一次，而外部副作用记录只有一条。

仓库有 fixture 服务和子进程崩溃测试覆盖这些故障窗口；它们不是现实供应商的验收。本次没有重新运行这些测试。

**例子：**测试 Server 先把 `effect-123` 写进自己的账本，再丢掉响应；重启后检查本地调用为 `uncertain`，Server 账本仍只有一条 `effect-123`。

### 9. 远端有幂等键，怎样用但不夸大成“只执行一次”？

可以从本地不可变调用 ID 生成远端幂等键。同一个调用重试时用同一个键、同一组参数；恢复时优先问远端“这个键有没有执行过”。远端确认已执行才补本地回执；确认没执行才能按规则重试；仍说不清就保持不确定。

这只能在远端真正遵守幂等约定、保留记录并能查询时减少重复执行。因为本地数据库和远端服务不是一个原子事务，不能笼统承诺 exactly-once（绝对只发生一次）。

**例子：**付款接口支持 `payment-42` 幂等键时，重试仍发 `payment-42`；若接口不保证记住这个键，OpenDot 不能承诺绝不会重复扣款。

## 五、Group 讨论、Coordinator、Speaker 和 Delegate

### 1. Coordinator 和 Speaker 的输出有什么区别？

Coordinator 是主持人，决定下一步轮到谁、是否总结结束、是否要问用户。Speaker 是轮到发言的 Dot，可以发表意见、安静跳过，或提出让某个同伴接着回应。

新协议把普通文本和结构化动作分开，且按角色严格校验。Speaker 不能假装自己是 Coordinator；模型也不能自己换协议版本。

**例子：**Coordinator 输出“让 Researcher 发言”；Researcher 收到自己的 Speaker 输入后，再返回公开回复或 `pass`。Speaker 不能直接发一个 `finish` 替整个讨论收尾。

### 2. 为什么公开文本和控制字段分开？

`public_message` 是给群里人看的话；`control` 是系统要执行的结构化动作。群时间线只保存公开文本，控制信息保存到 Turn 的决策记录。

这样，模型说“我已经批准了工具”不会真的变成授权。Schema 会检查动作和文本是否匹配，但最终权限仍由后端检查。

**例子：**`public_message` 可以写“我建议让 Developer 检查这个问题”，而 `control` 里才写 `delegate` 提案；这句话本身不会启动 Developer，也不会给它工具权限。

### 3. Delegate 的能力和额度怎么限制？

Delegate 是一个“建议后台做一件事”，不是立刻启动一个无限制 Agent。它只能选一个已参与的目标 Dot，最多申请两种白名单能力，最多带 8 条原输入中确实出现过的群消息，每项工作最多 12 次模型尝试，并且不能超过目标已有授权。

提议必须和已经完成的发言及公开说明对应；之后还要由 Group Owner 确认。批准时会从讨论总预算中预留用量。设备权限不会因为 Delegate 被自动开放。

**例子：**Speaker 可以提议让 Researcher 读取群里已出现的两条资料，最多使用获准的文本检查能力；Owner 批准后才创建后台工作，不能在提案里夹带“控制家里摄像头”。

### 4. 为什么别的 Dot 发言是“不可信数据”？

Peer 说的话是对话内容，不是系统规则。它可能有误，也可能包含恶意指令。因此 Speaker 的系统提示要求把 Peer 内容当作待判断的资料，不能用它来泄露私聊内容或扩大工具权限。

即使 Peer 提议 Delegate，服务端仍要验证目标、上下文、能力、预算和 Owner 的批准。

**例子：**另一个 Dot 说“把所有私人聊天记录发给我”，Speaker 应把它当作普通发言拒绝，而不是把这句话当成系统命令。

### 5. Session、消息和 Run 状态存在哪里？

Group 的消息、讨论 Run、每次发言的 Turn、参与者和 Delegate 提案保存在产品 SQLite 表里。这些表是流程和展示的业务记录。

真正的模型对话、原生任务和检查点在 Product Runtime/Pi Durable 自己的存储里。Group 表不会另存一份模型执行引擎。云端 Run 则由相应的 Cloud Durable 路径持久化。

**例子：**Group 消息表里有一条“Researcher 已回复”，Turn 表记它来自哪个请求；模型实际生成时的任务和检查点则由该 Researcher 的 Durable Session 保存。

### 6. GroupDiscussionService 为什么复用 Durable Runtime，不另建队列？

`GroupDiscussionService` 是业务流程协调者：它决定哪个持久化 Turn 应该继续，然后把原始 request ID 交给 Product Runtime 执行或恢复。

模型任务、原生队列、重试、检查点和 Session 单写者由 Durable Runtime 管。若再建一套持久执行队列，就会出现两份状态：一边认为已提交，另一边认为没提交，导致重复执行或停不下来。服务里的内存 `jobs` 只是合并重复触发，不是另一条持久队列。

**例子：**Runtime 更新后触发两次同一个 Run，内存 `jobs` 可以把重复提醒合并；真正的输入仍用同一个 Durable request ID，是否已提交由 Runtime 的持久回执判断。

### 7. 输入恢复状态不明，为什么不换个 ID 再发？

换新 ID 会告诉系统“这是一个全新的输入”，于是同一件事可能被模型执行两遍。恢复时应使用原来的 ID 和原来的内容查找/继续原提交。

如果能证明之前没提交，可以用原 ID 继续；如果已提交，就接回原结果；如果无法证明状态，就明确等待用户或结束为失败，留下回执，不要伪装成一次新任务。

**例子：**发言请求 `turn-8` 可能已被 Runtime 接收但 ACK 丢失。恢复时查 `turn-8`；不能另造 `turn-9` 再发同一段内容，否则会多一次模型执行。

### 8. 它为什么不是通用 Supervisor 或并行 Agent 框架？

普通讨论是有限参与者、有限轮次、有限预算的轮流发言。Coordinator 只能在服务端允许的名单中选人；同一个 Group 也只有一个活动讨论流程。

Delegate 是 Owner 审批后，转交给现有 Handoff 的有边界工作。它不是模型任意生子 Agent、任意递归委派或任意并行执行。并行后台工作也有各自独立的 Session 和授权。

**例子：**Coordinator 不能临时创建十个新 Agent 并让它们无限调用工具；它只能在既定参与者和预算内安排轮次，另有 Delegate 时也必须走 Owner 审批和 Handoff。

### 9. 如果支持多个并行 Delegate，怎样避免乱套？

每个工作都要有自己的唯一 ID、来源 Turn、固定参数、目标授权、预算、截止时间和结果回执；启动前要一次性预留总预算，不能让几个并发任务各自看见“还有额度”并超额运行。

同一个 Session 仍要遵守单写者；外部副作用要有独立回执或幂等键；结果要标明来自哪个 Delegate。最后还得提前规定何时汇总、结果缺失/失败/不确定怎么办、按什么顺序展示，避免把“没回消息”说成“已经完成”。

**例子：**两个 Delegate 同时研究同一文件时，可以并行读，但若都要改同一个文件就要串行或做版本冲突检查；汇总时分别标注“任务 A 成功、任务 B 超时不确定”，不能合并成一句“全部完成”。

## 六、读这份说明时要分清的证据等级

1. **源码**能说明当前代码试图怎样处理事情。
2. **单元测试/Fixture**能证明特定输入、状态和故障注入下的行为，不等于真实 Provider、真实设备或真实用户环境。
3. **真实模型测试**能验证有限模型和配置下的集成表现，不自动代表长期稳定或用户价值。
4. **线上用户证据**才适合回答用户是否真的省时、是否满意、是否愿意持续使用。

本说明是根据项目代码、测试和文档整理的架构解释，不是用户研究报告，也不是本次重新执行的测试报告。尤其是测试是否由某人亲自运行、真实用户是否满意，都不能只看源文件来断言。

**例子：**看到一个测试文件，只能说明仓库有这个测试；只有实际执行记录才能说明某次运行通过，而真实用户是否觉得好用还需要用户反馈和线上数据。

## 七、从页面到接口的全链路设计

### 1. 为什么页面不直接请求模型，而要经过 OpenDot 接口？

页面是用户操作入口，不能自己决定模型权限、Workspace 归属、队列状态或工具能否运行。浏览器把用户动作交给 OpenDot API，由服务端识别当前登录用户、检查资源权限、保存状态，再决定是否交给 Runtime 执行。模型 Provider 的密钥和服务端配置也不应暴露给浏览器。

**例子：**用户在聊天框输入“总结这个工作区的资料”，页面只提交消息和目标聊天 ID；后端先确认用户能访问这个 Workspace，然后才把输入交给对应的会话执行。

### 2. 页面、状态管理和 API 客户端分别负责什么？

页面组件负责展示和收集操作，例如聊天输入框、渠道设置页；Zustand Store 负责调用接口、更新本地状态和处理页面交互；统一的 `apiFetch` 负责带上 Cookie、设置超时、解析错误，并在登录失效时跳转登录页。这样页面不用每个地方都重复实现认证和网络错误处理。

**例子：**聊天页面把文字交给 `chat` Store 的 `sendMessage`，Store 调 `api.post('/api/messages', ...)`；渠道设置组件则通过 `channel-accounts` Store 读写 `/api/channel-accounts`。

### 3. 一个请求进入后端后，先经过哪些检查？

普通 API 会经过登录认证；随后路由验证请求结构和字段，再检查资源是否存在、归谁所有以及当前用户是否有权操作。工作区消息还会检查工作区访问权限；Host 执行模式另有角色权限。很多其他用户的资源会以 `404` 返回，避免让调用者探测资源是否存在。

**例子：**即使页面把别人的 `chatJid` 填进请求，`POST /api/messages` 也会在后端查工作区并执行 `canAccessGroup`；页面隐藏按钮不是安全边界。

### 4. 业务规则、数据库和 Runtime 谁负责什么？

路由层负责把请求串起来，并调用领域函数、权限检查、数据库访问和 Runtime 服务；SQLite 保存消息、工作区、账号等业务状态；队列和 Runtime 负责实际运行会话。不是每个操作都经过一个单独的“业务服务层”，所以要按具体路由查看它实际调用的规则和持久化函数，不能只凭目录名称假设分层。

**例子：**`/api/messages` 验证请求与工作区权限后，普通消息进入 Web 消息处理流程并写入消息记录；符合 Durable 条件的消息则提交给产品 Runtime 并返回它的提交回执。

### 5. 发消息接口返回成功，是否代表模型已经回答？

不一定。`POST /api/messages` 的正常路径会返回消息 ID、时间戳、运行 ID 和 `started`、`queued` 或 `steered` 等处理回执；它说明后端接受并安排了输入，不等于模型已生成答案，更不代表外部工具或投递成功。部分 Durable 路径返回的是持久提交回执，含义也应按该 Runtime 的收据理解。

**例子：**已有任务正在运行时，新消息可能返回 `queued`。页面可以显示“已排队”，但不能显示“任务已完成”。

### 6. 多条消息同时到达时，谁决定先后和如何处理？

后端根据会话和运行状态安排输入，页面可以请求 `queue` 或 `steer` 等 follow-up 行为；消息文本和运行进度不是由前端本地顺序决定。Durable 产品 Session 有专门的提交/队列协议；旧执行路径也由服务端队列处理。前端收到回执后展示对应状态，而不应自行假设消息已经执行。

**例子：**Agent 正在读文件时，用户再发一条“顺便列出风险”，若选择排队，后端保存为待处理输入，等当前运行到适当边界后再接着执行。

### 7. 后端结果怎样回到页面？断线后怎么办？

HTTP 用来提交请求和返回即时回执；WebSocket 用于推送新消息、流式内容、状态和部分连接状态。聊天页面收到 `new_message` 与 `stream_event` 后更新显示；断线重连时可接收流式快照，消息列表也有从后端重新加载的路径。因此 WebSocket 是实时更新通道，不是唯一的持久状态来源。

**例子：**模型正在生成时，页面通过 WebSocket 逐段显示文字；如果浏览器断网，恢复后重新获取消息和运行快照，而不是把浏览器内存里的半句话当作最终答案。

### 8. 请求超时或页面报错时，能不能直接再点一次？

先看这类接口有没有明确的幂等协议。前端 API 客户端有请求超时和网络错误处理，但网络超时只表示浏览器没有及时拿到响应，不证明后端没有收到请求。Durable 输入要求稳定的 `requestId`，同一请求用相同 ID 和参数重试；常规请求不能一概假设都具备相同的去重保证。

**例子：**Durable 消息提交后浏览器超时，应使用原 `requestId` 查询或重试；若换一个 ID 重新发送，可能会被当成另一条新输入。

### 9. 怎么验证这条全链路真的可用？

应分层验证页面状态、API 请求格式、认证与 ACL、数据库写入、队列/Runtime 执行、WebSocket 更新和断线恢复。测试可以证明特定请求与故障场景的行为；真实模型、Provider、平台和用户工作流仍要用独立的集成验证和线上指标评估。可追踪的请求 ID、消息 ID、运行 ID能帮助定位“卡在页面、接口、队列还是外部服务”。

**例子：**若页面显示“已发送”但对话没有回复，依次核对 API 回执、消息是否落库、运行是否启动、流事件是否发出；仅截图看见按钮变灰，不能证明端到端成功。

## 八、多渠道接入

### 1. “渠道账号”和“聊天对象”有什么区别？

渠道账号是用户配置的一套平台身份与凭据，例如一个 Telegram Bot 或一个飞书应用；聊天对象则是这个账号能收到消息的群聊或私聊。同一个用户可以为同一平台配置多个账号，账号拥有独立连接、凭据和默认工作区。凭据使用 Secret 引用保存，公开 API 返回账号元数据和是否已配置凭据，不把秘密原文发回页面。

**例子：**用户可以有一个 Telegram Bot 专门接收家庭群消息，另一个 Bot 接收工作群消息；两者是两个账号，不应因为平台相同就混成一条连接。

### 2. 用户怎样把平台账号接进来？所有渠道都一样吗？

不一样。部分平台用 App ID/Secret 或 Bot Token；微信、WhatsApp 等 QR Session 渠道要走扫码授权和状态轮询。页面创建或编辑账号时调用 `/api/channel-accounts`，扫码流程再使用账号级 onboarding 接口；后端验证凭据格式、保存 Secret、尝试重载连接器，并分别记录授权状态和传输连接状态。

**例子：**创建一个 Telegram Bot 账号时填写 Bot Token；WhatsApp 则先启动 onboarding，页面显示二维码，用户扫码后持续查询状态，完成授权后连接才进入可用状态。

### 3. 为什么要有统一的渠道接口，又为什么不能把渠道当成完全一样？

统一的 `IMChannel` 接口让主服务用相近方式连接、收消息和发送回复；每个平台的适配器仍负责处理各自 SDK、消息格式、连接方式和限制。项目还用能力表记录每种渠道支持哪些绑定、话题映射、流式更新、文件发送和激活策略，页面和业务逻辑不能假定所有渠道都具备同一功能。

**例子：**飞书可以通过流式卡片更新回答，微信当前能力表不支持流式更新和文件发送；系统不能把飞书的交互方式直接当作微信也支持。

### 4. 收到一条平台消息后，系统怎样知道它应该进入哪个工作区或会话？

账号连接收到消息后，先把渠道账号 ID 纳入稳定的聊天地址，再根据渠道挂载关系解析目标 Workspace、主会话或 Runtime Session。一般工作区绑定接收群聊，Runtime Session 绑定接收私聊；具备原生线程能力的平台还可以把不同话题映射成独立会话。没有有效绑定或目标已过期时，系统应拒绝路由，而不是猜一个看似合理的目标。

**例子：**飞书群的某个原生话题绑定到工作区后，话题里的消息进入该话题对应的独立 Runtime Session；它不会和另一个话题的对话混在一起。

### 5. 多账号、多用户怎样避免串号或跨租户？

账号记录带有 owner；每个渠道聊天地址带账号作用域，避免同一平台上不同 Bot 的外部群 ID 被误认为同一个对话。连接管理器在处理入站消息时会检查用户和账号仍然有效、账号仍启用且 owner 匹配；数据库查询和路由也按当前用户限制。账号状态事件只推送给账号所有者。

**例子：**两个用户都接入了 Discord，甚至平台侧标识相似，仍需按各自的账号 ID 和 owner 区分；A 用户收到的状态更新不能推到 B 用户的页面。

### 6. 群聊、私聊、@提及和原生话题有什么业务差异？

绑定和触发方式由渠道语义与策略决定。群聊绑定到 Workspace；私聊可以绑定到 Runtime Session。部分渠道有 `always`、`when_mentioned` 或 `disabled` 等激活策略，也有 owner-only 等受众限制；支持原生话题的渠道可为每个话题建立独立上下文。策略由后端按消息元数据和记录的绑定执行，不能只依赖页面显示。

**例子：**飞书普通群设置为“被 @ 才激活”时，第一次 @ 可以建立话题会话；之后在同一话题继续交流时，系统按话题上下文处理，不必把它误当成新群聊。

### 7. 平台上的发言者是否都可以让 Agent 执行任务？

不能默认可以。入站消息除了需要找到绑定，还可能经过聊天授权、配对、群成员 allowlist、@门控和 owner 身份校验；破坏性命令及部分控制操作还受渠道原生 sender ID 的 owner 约束。平台有管理员身份不等于 OpenDot 中的工作区所有者，权限必须按项目自己的 owner 和策略检查。

**例子：**一个人能在群里发普通问题，不代表他可以用 `/clear` 清掉工作区历史；清理操作还要检查该发言者是否是被记录的 owner。

### 8. 回复、流式更新和文件发送是否能保证送达？

不能一概保证。渠道能力和平台连接状态决定能否流式更新、发送附件或使用特定卡片；发送代码还会依据当前 Turn 的 `ChannelTurnContext` 和源会话来确定投递目标，避免从“最近一条群消息”猜收件人。平台返回的发送结果只能证明对应阶段的处理结果，不能据此推断对方已经阅读。

**例子：**某次飞书话题中的运行需要回传图片，目标应取自这次输入的 Turn 上下文；不能因为最近另一个群刚发过消息，就把图片送去那个群。

### 9. 新增一个渠道，真正要做的不只是接上 SDK 吧？

还要实现凭据与连接生命周期、入站消息规范化、账号作用域、聊天授权和绑定路由、消息发送与附件策略、断线重连、状态通知、能力声明、用户配置界面和测试。要分别测试正常消息、无绑定、权限拒绝、账号断开、平台不支持的能力和投递失败。即使接口适配和单测通过，也不能代替真实平台账号下的端到端验证。

**例子：**接入一个新聊天平台，除了能登录，还要证明“群消息进对的 Workspace、私聊不串到群会话、断线后状态可见、账号删除后连接和绑定都被清理”；只看到 SDK 返回 connected 远远不够。

## 十、五项有代表性的设计：从问题到兜底

下面五项不只是“用了什么技术”，而是分别处理五类产品风险：会话重启后还能不能接着跑、模型上下文能不能被检查、工具授权能不能对应到具体操作、调度任务会不会被重复领取，以及多个 Agent 协作时能不能约束它们的发言和行动。

这里的“设计灵感”是根据代码结构归纳出的工程动机，不等于作者留下了相同措辞的设计访谈或决策记录。下面的场景例子用于解释机制，不代表真实用户案例或真实外部服务的实测结果。

### 1. Durable Session：让长期会话能恢复，但不假装副作用可以重来

**设计灵感——把“聊天记录”与“正在发生的执行”分开看。**  
普通聊天记录解决的是“用户和助手说过什么”；长期运行还要回答另一组问题：这条输入有没有被接收、哪个进程正在执行、工具是否已经发出去、进程重启后该从哪里继续。只保存对话文本不够，因为从聊天文本无法可靠推断一次付款、发信或设备控制到底有没有发生。

**为什么要这样设计？**  
执行可能跨越很长时间，期间会遇到服务重启、网络中断、浏览器超时、重复提交和工具响应丢失。若系统把每次失败都当成“什么都没发生”，恢复时重跑就可能造成重复副作用；若只保存“正在执行”，又可能永远不知道它是否已经停下。因此需要分别保存会话运行状态、输入收据和需要保守处理的副作用状态。

**怎么设计？**  
Pi Durable 管理原生会话、提交和恢复；`PiDurableRuntimeAdapter` 把 OpenDot 的 Session 身份、产品输入和运行接口接到 Pi Durable 上。输入账本按 Session 保存 request ID 对应的请求正文摘要，既能识别同一请求的重试，也能拒绝“相同 ID、不同正文”的请求。另一个 `.owner.sqlite` 文件通过 SQLite 的 `BEGIN IMMEDIATE` 写事务协调本机单写者：同一 Durable 数据库不能由两个 Harness 同时拥有。调用外部副作用时，状态会区分尚未派发、正在派发、已完成和结果不确定等阶段；进入可能已产生副作用的派发阶段后，不能轻易当作“没做过”再发一次。

**选型与取舍。**  
这里复用 Pi Durable，避免 OpenDot 自己再造一整套会话检查点和恢复引擎；OpenDot 自己补产品级身份、输入绑定和本机 owner 协调。SQLite 锁的好处是机制直接、和当前单机部署形态匹配，也不需要维护外部协调服务；代价是它不是跨主机选主协议，且依赖本机文件系统和 SQLite 锁语义。输入摘要只能证明“请求内容和之前绑定一致”，不能证明外部副作用恰好执行一次。

**错误与兜底。**  
如果 owner 已被另一个 Harness 占用，应明确拒绝第二个执行者，而不是同时启动后希望队列自行排好。相同 request ID 携带不同内容时应冲突失败；不能把它当新请求覆盖旧绑定。进程在 `dispatching` 阶段崩溃后，如果无法从服务端回执判断结果，应标为 `uncertain`，让上层查账、对账或请求人工确认，而不是伪造 `completed` 或自动重试。若未来要支持多主机，必须重新设计分布式 owner、fencing token 和副作用幂等协议，不能只把 SQLite 换成远端数据库。

**完整例子。**  
用户提交“给供应商发送这份报价”，浏览器和服务端都使用同一个 `requestId`。服务端先把这个 ID 与“发送报价”的正文摘要绑定，再让 Durable Session 接收输入。若网页等待响应时超时，用户用同一 ID 重试，系统可以识别这是原请求，不另造一条新的会话输入。模型随后准备调用发信工具，审批通过后，Host 记录进入派发阶段并向邮件服务发送请求。如果邮件服务已经接收、但确认回包丢了，服务只能知道“请求可能已生效”，不能断言邮件一定没发。此时应保留不确定状态，按邮件服务的消息 ID 查询或由用户核对；不能为了让界面变绿而谎报成功，也不能盲目再发一封。

### 2. PromptPlan 与 Context Budget：让上下文从“拼接字符串”变成可检查的计划

**设计灵感——把提示词当成一次有来源、有预算的构建产物。**  
Agent 的输入不只是用户眼前的一句话，还可能包括平台规则、Agent Profile 的身份与工作流、Workspace 文件、Skills 和其他运行上下文。若只是把这些内容随手拼成一个大字符串，出现重复、漏掉必需规则或把错误 Workspace 的内容混入时，很难定位是哪一块造成的。

**为什么要这样设计？**  
上下文错误会同时影响安全性、行为质量和运行成本。缺少必需规则可能改变 Agent 行为；重复块会浪费上下文窗口；跨 Workspace 拼错来源会造成数据泄漏；超长提示词可能在调用模型时才失败。如果 UI 显示“已选 Skill”，但 Runner 实际加载了另一份内容，用户也无法判断 Agent 到底运行在什么配置上。

**怎么设计？**  
Runner 把平台身份、行为规则、Profile Prompt 等来源整理成 Prompt Blocks。每块具有稳定 ID、版本、作用范围、owner、是否必需、来源条件及内容摘要；计划生成时检查重复 ID、空的必需块，并计算整体字节数和估算 token 数。达到警告线时记录 warning，超过硬阈值就拒绝构建。Context Budget 负责运行前预检；Runtime 初始化后还可以从 SDK 读取实际 context usage。Skill 的候选发现、精确解析和 Runner 实际可见目录则需要按选中清单对齐，而不能把“UI 上选中”直接当作“Runner 已正确加载”。

**选型与取舍。**  
PromptPlan 的收益是能回答“本次上下文由哪些块组成、每块来自哪里、为什么出现”，便于测试、审计和排错；代价是要维护 block 元数据和来源映射。预检可以阻止意外构造极大的提示词，但 token 估算不等于特定模型 tokenizer 的真实计数；Runtime usage 更贴近实际调用，但依赖 SDK 对 usage 的报告，也不能保证模型永远不会因上下文窗口或服务端策略拒绝请求。两层检查互补，不应把静态预算宣传成精确费用账单。

**错误与兜底。**  
必需块缺失或为空、block ID 重复、Prompt 超过硬阈值时应在构建/预检阶段明确失败，不能默默删掉规则后继续运行。精确选择的 Skill 被禁用、删除或缺少内容时应报告配置不可用，不静默换成另一个同名能力。即使预检通过，若模型 Provider 最终仍返回 context overflow，也应把运行失败原因反馈给用户，并按 Runtime 支持的压缩/截断策略处理；不能把“预检过关”显示成“模型一定能接受”。任何未来摘要都应保留可追溯来源和 Workspace 权限边界，并单独验证关键否定、期限和约束有没有在摘要中丢失。

**完整例子。**  
某个工作区的 Agent 由平台身份、用户写的工作流程、项目内的 Skill 和几段历史对话组成。构建计划时，系统发现工作流程块被重复添加，就应指出重复块并修正组装，而不是把两份规则都交给模型；如果必需的平台行为块为空，也不应该继续启动。若计划估算超过硬阈值，预检直接挡下并说明上下文过大。假设预检估算通过，但运行时历史对话继续增长，最终 Provider 仍返回“上下文超限”，这说明静态预算不是最终保证。系统应按 Runtime 实际支持的恢复策略缩减或压缩上下文，无法恢复时明确报错，而不是伪装成一次成功回答。

### 3. MCP Consent 与逐次审批：把“允许某类工具”收紧到“允许这一次具体操作”

**设计灵感——长期授权说明能力边界，单次审批说明这次具体意图。**  
用户同意某个 Session 使用一个 MCP Server，不代表未来该 Server 的工具清单、配置和参数永远不变；同样，同意“可以使用邮件工具”，也不等于同意任意收件人、任意正文、任意时间都能发信。授权范围和实际操作必须分开记录。

**为什么要这样设计？**  
工具调用可能造成外部副作用，且请求可能在网络上已经送达后丢失响应。模型生成的参数也可能和用户界面上看到的审批内容不同。如果系统只记一个“已授权”标志，就不能证明用户批准了哪项能力、哪组参数，也很难区分失败、成功和结果未知。

**怎么设计？**  
Session Consent 对会话当时允许的 Server、工具能力和相关配置建立快照；调用意图则被规范化，并绑定 Server/operation、来源、会话、参数摘要和调用 ID。审批前和实际派发前都会校验当前运行身份、授权状态及具体参数；用户决定还绑定参数摘要与 request ID。账本区分 `pending`、`approved`、`dispatching`、`completed`、`uncertain` 等生命周期状态。调用发出后，只有 Host 根据实际执行过程和回执更新完成状态，模型文本本身不能证明工具已完成。

**选型与取舍。**  
项目用持久账本和参数摘要获得可审查、可恢复的审批边界，而不是只依赖对话里一句“用户同意了”。这样会增加状态转换、过期处理、摘要规范化和授权复核的复杂度；而且账本只能约束明确接入这条协议的工具路径。Runtime 原生工具、第三方 MCP Server 或其他外部 API 不会因为项目存在这套审批就自动全部受其保护。参数摘要证明审批和派发的是同一组参数，不证明远端服务支持 exactly-once。

**错误与兜底。**  
授权快照过期或配置变化时应拒绝旧授权继续扩展权限，要求重新建立有效 Consent。调用参数摘要不匹配、同 request ID 对应不同决定、审批过期或 Host 再校验失败时应拒绝执行并保留可解释错误。派发已开始但外部结果不明时标记 `uncertain`，先用外部查询或幂等键对账；无可靠证据前不自动重发，也不把撤销授权解释成“已撤回远端副作用”。撤销通常能阻止后续 dispatch/调用，但不一定能取消已经进入外部系统的请求。

**完整例子。**  
用户在 Session 中允许一个 MCP Server 提供“创建日历事件”，随后 Agent 提议“周五 15:00 给团队创建评审会”。系统把工具、日历和参数摘要呈现给用户；用户批准后，Host 再检查 Consent 没有失效、参数摘要仍一致，然后才进入派发阶段。如果此时管理员撤销了 Server 授权，尚未派发的调用应被拦截；若请求已经发出，则只能停止后续调用并查询日历确认事件是否创建。若调用响应超时，账本保留 `uncertain`。有外部幂等键时可以用同一个键查询/重试，但是否去重仍取决于日历服务对这个键的实际契约。

### 4. Task Run 租约与恢复：把“计划要做什么”和“这一次谁在执行”分开

**设计灵感——一个计划可以重复触发，但每次触发都应有独立身份。**  
定时任务的定义描述未来规则，例如每天几点执行；Task Run 则表示某个具体时间点的执行实例。把两者混成一个“任务正在运行”标志，会让计划修改、重启恢复、重复领取和历史审计互相影响。

**为什么要这样设计？**  
调度器可能因进程重启、时钟变化或并发检查而多次看到同一个到期任务；任务执行还可能比调度间隔更长。如果没有持久 Run 身份和领取所有权，两个调度循环可能都启动同一轮工作，或者旧进程在新进程接手后迟到写回结果。另一类问题是用户修改计划后，正在执行的那一轮究竟使用旧参数还是新参数会变得不清楚。

**怎么设计？**  
调度器把到期 occurrence 物化为持久 Task Run，并把执行定义快照及版本绑定到该 Run。worker 通过 owner/token lease 领取运行，执行期间定期续租；提交完成、失败或释放重试时都要携带原 owner 和 token 校验。token 充当 fencing 身份：租约丢失或被新执行者取代后，旧执行者的结算不应覆盖新状态。运行前的安全重试和真正跨过执行边界后的失败处理也要区别开；对错过的周期窗口，系统记为 `missed` 并推进计划，而一次性任务有自己的补跑规则。

**选型与取舍。**  
把 Run 落到数据库而不是只用内存定时器，能在重启后重建未完成工作并保留历史；租约和 token 让多个执行尝试之间有可验证的所有权边界。代价是要处理租约时钟、续租失败、进程停止、运行定义快照和重复 occurrence 等复杂情况。数据库 token 只能拒绝旧 worker 更新本地 Run 状态，并不会撤回它已经发出的邮件或其他外部动作；所以它不是 exactly-once，也不能单凭源码证明多节点调度已经过生产验收。

**错误与兜底。**  
如果执行在尚未越过副作用边界前安全失败，可按有界退避释放租约并重试；达到安全重试上限则让 Run 以失败结束并保留错误。续租失败或数据库错误时应停止当前执行，避免一个已失去所有权的 worker 继续运行。若租约到期后另一个 worker 已领取同一个 Run，旧 worker 迟到的结果必须因 token 不匹配而不能结算覆盖。对已经可能产生副作用的阶段，不能把“租约过期”当成“操作没发生”，应先查外部回执或标记不确定。周期任务 missed 与一次性任务补跑策略也要如实呈现，不能把错过的每个时间窗口都伪装成已执行。

**完整例子。**  
用户设定每晚 21:00 生成一份工作日报。调度器在到期时创建对应日期的 Run，并记录当时的任务定义快照。worker A 领取 Run，获得 token `T1`，开始读取数据。若 A 在启动外部动作前崩溃，Run 可按安全重试策略重新排队；worker B 领取后获得新的 token `T2`。A 后来恢复并尝试用 `T1` 写“完成”，数据库应拒绝这次过期结算。若 A 在崩溃前已经把报告发到外部聊天平台，而平台回执丢失，则 B 不能因为自己拿到新租约就确信报告没发，应先查询消息回执或进入待核对状态。token 解决本地所有权冲突，不替外部平台提供幂等性。

### 5. Bot Group Discussion：用结构化协议约束协作，而不是让模型自由编排一群 Agent

**设计灵感——多人协作需要分清“说给人看的话”和“要系统执行的动作”。**  
Coordinator 安排谁发言，Speaker 产出回复或选择跳过；如果它们只输出一段自由文本，程序就很难安全判断一句话究竟是公开回答、结束讨论、等待用户，还是创建 Delegate 工作。把可执行意图设计成明确协议，比从自然语言中猜控制动作可靠。

**为什么要这样设计？**  
模型输出可能不完整、格式错误或夹带超出职责的请求；不同角色权限也不应混在一起。让 Speaker 在公开文本里写一句“我安排另一个 Agent 去操作”，不能自动等于授权系统启动工具。Delegate 还会带来新的预算、上下文、工具权限和结果归属问题。需要让服务端验证谁能做什么，而不是让模型一句话决定。

**怎么设计？**  
协议用严格 Schema 校验 Coordinator 的 `speak`、`finish`、`wait_for_user`，以及 Speaker 的 `reply`、`pass` 等决定。V2 将 `public_message`（面向用户/群成员的文本）与 `control`（结构化控制动作）分开，并校验两者是否匹配该动作。Delegate 请求限制目标 Profile、说明文字、可用工具能力、模型尝试次数和被引用的上下文消息 ID/条数；执行仍要经过服务端的 Owner 审批和持久工作记录。Group 讨论复用 Durable Runtime 管理会话上下文和执行所有权，不另建一套竞争的 Agent 队列；协作消息及 Run 状态则由 Group 相关持久化层记录。

**选型与取舍。**  
严格版本化 JSON/Schema 比“让模型自由发挥、服务端用关键词猜意图”更容易验证和演进，也能拒绝额外字段和超额请求。代价是模型输出格式不正确时需要失败或重试，Schema 变更要考虑协议版本和历史运行兼容；固定工具清单和预算也限制了它的通用性。复用 Durable Runtime 减少重复实现会话恢复和单写者机制，但不意味着 Group Discussion 自己的消息、调度与审计状态可以省略。这个架构是受限协作流程，不是能动态规划、无限扩张并任意并行执行的 Supervisor。

**错误与兜底。**  
空输出、非法 JSON、未知协议版本、角色不允许的 action 或额外字段都应明确拒绝，不应靠猜测或静默降级成另一个角色的决定。Delegate 超出工具、次数或上下文限制时，在创建工作前拒绝并说明原因；用户没有批准时不能启动。其他 Speaker/Delegate 发来的文本要按不可信数据处理，不能把它当系统指令或权限证明。恢复时若无法确认某条 Durable 输入有没有被接收，应查询同一个 request ID 或等待用户处理，不能换新 ID 伪造一次重提。多个 Delegate 若未来并行，还要额外解决同一 Session 单写者、共享副作用去重、预算预留和结果聚合标准。

**完整例子。**  
一个用户在 Group 中询问“这段代码的风险有哪些？”Coordinator 可以决定先让 Reviewer 发言；Speaker 返回一段公开分析，或通过 `pass` 表示没有补充。若讨论需要另一个角色检查文件，Speaker 可以提出带目标 Profile、上下文消息 ID 和受限工具能力的 Delegate work，但这只是结构化提案，不是自动授予文件写权限。Owner 批准后，服务端才创建持久工作并交给 Durable Session 执行。若模型输出多了一个未定义的“直接部署”字段，Schema 应拒绝整个决定；若被委派的工作已经提交但确认响应丢失，恢复时查原 request ID，而不是新造一个 ID 再跑一遍。最后汇总时区分“已验证的发现”“某个 Delegate 未返回”和“仍需用户确认”，不能把不完整结果包装成全员完成。

### 五项设计放在一起看

这五项共同遵循一个思路：**模型可以提出理解和行动建议，但身份、授权、状态转换、重试边界和结算由可检查的程序协议负责。** Durable 管执行恢复；PromptPlan 管输入由什么组成；MCP 审批管一次外部调用是否被允许；Scheduler lease 管一个 Task Run 由谁结算；Group 协议管协作角色能发出什么决定。它们能降低重复执行、越权和状态误报的风险，但并不能消除模型错误、外部服务不确定性或需要人工判断的情况。

**综合例子：**某个定时 Run 让 Coordinator 汇总工作区进展，先构建有来源的 PromptPlan，再由 Durable Session 接收稳定 ID 的输入。Coordinator 提议 Delegate 读取两个指定文件；Schema 检查请求符合工具和预算上限，Owner 批准后才创建工作。Delegate 发现需要调用 MCP 写入工具时，仍须通过独立 Consent 和参数审批。Scheduler 只允许当前 lease token 对该 Run 结算。任一环节遇到超时，都按对应边界区分“还没执行”“已经执行”“结果不确定”，而不是把所有错误统一标成失败后从头重跑。
